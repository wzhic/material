# 项目形态与发布单元-ADR-0001

## 状态

已接受，2026-08-18；决策人：用户。

## 上下文

产品由 macOS 客户端、Windows 客户端和统一后端服务组成。两个客户端业务功能完全一致并共享代码，但运行环境、打包、签名、安装、升级和回退不同。预计由 1 人维护，需要减少重复治理，同时保留每个产物的真实发布边界。

## 考虑的方案

1. 把整个产品视为一个 single 项目、共用一个版本：简单，但无法表达三个独立发布和回退结果。
2. 三个独立仓库：边界清楚，但共享客户端代码、兼容矩阵和单人维护成本更高。
3. 一个 monorepo、三个独立发布单元：共享治理和代码，同时分别记录构建、版本、发布与回退。

## 决策

采用方案 3，正式分类为 `M + multi`。monorepo 是代码存放方式，不改变 multi 的发布事实。

- macOS 与 Windows 客户端共享业务代码、功能一致。
- macOS、Windows、backend 分别使用自己的版本、自动验证证据、真实环境验收、发布记录和回退条件。
- 跨单元需求建立协调任务和兼容矩阵；每个可独立验收的功能点使用独立任务、分支和 PR。

## 后果

正面后果：单人可以统一文档、治理和共享实现；跨单元变更可在同一仓库被核对。

成本与约束：PR 与 `main` push 的治理 CI 都覆盖三个平台，同一分支的新提交取消尚未完成的旧运行以控制私有仓库分钟数；版本不能只使用一个仓库 tag；发布和回退必须核对 API、身份、文件格式和 SQLite schema 兼容；共享代码仍要分别验证平台行为。`windows-latest` 治理 CI 只证明治理入口的 Windows runner 兼容性，不等于真实 Windows 客户端安装、升级、卸载或业务验收。

## 重新评估触发条件

- 某发布单元需要独立权限、团队、合规或发布节奏；
- 仓库体积或 CI 成本妨碍维护；
- 客户端业务实现无法继续安全共享；
- 引入第四个独立服务或数据边界；
- 风险条件使项目需从 M 升级为 L。
