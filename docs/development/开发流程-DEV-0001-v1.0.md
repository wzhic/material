## 开工顺序

1. `taskctl` 读取唯一当前任务，确认需求版本、目标、发布单元、依赖和允许路径。
2. `reviewctl` 验证用户对话回执是否与当前范围和验证计划一致。
3. `reconcile` 核对分支、工作区、阶段、文档、回执和验证状态。
4. 三项都无阻断后，才在批准路径内开发。
5. 完成实现后运行批准的全部验证，再运行 `reconcile`。
6. push 和 PR 由 CI 在干净环境重复验证；合并后在主分支再次验证。

命令参数以 `tools/governance/*.py --help` 为准。不得绕过工具手工推进阶段或伪造验证结果。

`reviewctl` 没有“创建审核申请”命令；需求、任务、验证/回退计划和 `REVIEW_PENDING` 状态共同构成申请。用户在当前 Codex 对话中明确批准、拒绝、撤销或豁免后，Codex 才可使用 `record-conversation`；工具自动绑定当前治理状态并原子追加回执。旧 `record` / `waive` 保持禁用，任何回执文件仍不得直接编辑。

R003 是最后一份 OpenSSH 签名迁移回执，历史 `review_authority` 仅用于复验 R002/R003。后续回执采用 `conversation-v1`，不要求签名，也不提供密码学身份或人在场证明。范围、提交、检查、摘要、有效期或项目策略漂移时仍必须失败关闭。

## 需求拆分与分支

- 先按用户可独立验收的功能点拆需求，再按发布单元拆实现任务。
- 一个功能点只在一个分支开发；第二个独立功能点使用新的任务、回执和分支。
- 每个任务把工作分支和目标 `base_branch` 一并纳入 scope 回执；分支格式为 `codex/<req-id>-<task-id>-<readable-slug>`。词语简短、易读，不堆叠内部术语，除 G0 bootstrap 外工作分支不得等于 base branch。
- 跨三个发布单元的功能使用一个协调任务管理兼容与顺序，并建立独立实现任务和 PR。
- macOS 与 Windows 共享业务代码时，可建立一个客户端共享实现任务；两个平台必须分别提供构建、安装/升级/卸载和行为验证证据。Windows CI runner 只证明自动治理入口执行，不替代真实 Windows 产品验收。
- 修复缺陷也需要独立任务和分支。只有同一根因、同一验收标准的修复才能放在一起。

初始 G0 是建立根信任的历史特殊阶段。普通任务在需求批准前可在 `docs/requirements/**`、`docs/decisions/**` 和 `project-control/proposals/**` 准备本地文件；进入 `IN_PROGRESS` 后可在批准路径内持续编辑和测试。上述准备权不延伸到应用初始化、脚手架或依赖选择。

空仓库首次 G0 push 必须使用两步证据：根内容提交 A 的 workflow 运行全部批准检查，但保持 `bootstrap_pending` 且不记录 CI PASS；`taskctl` 记录 A 后形成的控制提交 B 只能修改受保护治理记录，B 再次运行全部检查并产生可在线核验的 `bootstrap_control_head`。该历史入口固定 GOV-0001/main/空远端，只能使用 `bootstrap-commit/bootstrap-push --stage content|control`。后续普通任务沿用 A/B 不变量，但改用 `commit-task/push-task` 处理独立功能分支。两类入口都拒绝直接 Git 写操作、force push、空提交、跳过验证和控制提交中的普通内容。

## 范围控制

任务开始前必须记录：

- 需求文档和版本；
- 允许路径与禁止路径；
- 功能点和明确非目标；
- 前置依赖与后置影响；
- 数据、接口、鉴权和兼容影响；
- 验证计划、证据位置和回退计划；
- 假设、未决事项及最迟确认阶段。

发现需要修改批准范围外的文件时，停止当前任务，先更新需求，再通过 `taskctl revise-scope` 递增范围版本并返回起草/待审核，然后请求新回执。任务已提交或结束后不能原地改范围，必须新建任务。普通 `transition` 不能倒退状态，也不能替代范围修订。不得把“顺手修复”“格式化”或“重构”当作隐含授权。

`project-control/tasks/**`、`project-control/reviews/**` 和 `project-control/current-task.json` 是受保护记录，禁止直接编辑。任务及当前任务只由 `taskctl` 写入，回执只由用户控制的 `reviewctl` 流程写入；损坏或冲突时保留现场并由 `reconcile` 报告。

任务到达 `LOCAL_VERIFIED` 后，普通源代码、文档和配置冻结：

- 同一范围内发现缺陷时，先通过受控返工/失败流程使相关验证证据失效，再修改并重跑受影响检查。
- 范围、允许路径、需求版本或验证计划变化时，必须执行 `taskctl revise-scope`，递增 `scope_version` 并重新获得 scope 回执。
- 已提交任务需要改范围时建立新任务与新分支，不改写旧任务来让证据继续生效。
- `LOCAL_VERIFIED` 且尚未提交时，同范围返工可直接使用 `taskctl reopen` 归档旧证据，无需再次询问用户；从 `COMMITTED` 因 CI 失败阻断时，普通任务使用 `recover-blocked` 追加返工，重新执行完整 local gate，禁止 force push。

## 脚手架与依赖

- 技术栈确定且用户审核后，才允许初始化应用。
- 使用对应官方生成器或经审核的可信脚手架，先在独立临时目录运行，核对文件清单、版本、许可证、脚本、网络下载和默认遥测，再把批准内容引入仓库。
- 不手工仿造脚手架，不自行写 `package.json`、锁文件、项目清单等应用依赖文件来假装生成结果。
- 新依赖必须说明用途、替代方案、许可证、安全/维护状态、包体/运行成本、版本固定和移除方案，并进入任务审核范围。
- G0 治理工具只使用 Python 标准库，不构成应用技术栈选择。

## 实现和注释

- 命名表达业务含义，使用仓库约定的同一词汇；避免连续缩写和层层抽象。
- 注释只用于解释为什么这样做、必须保持的不变量、兼容要求、安全边界、前置条件和后置条件。
- 不写复述语句的注释，不在注释里记录作者、日期或变更历史。历史属于任务、Git 和决策记录。
- 共享客户端代码需要明确平台适配边界；平台差异不得散落为无法追踪的条件分支。
- 任何持久化变更都要有 schema 版本、迁移验证、备份和回退/前滚方案。

## 需求文档版本

- `v1.0`：首次获准实现的完整需求。
- 次版本增加：不改变目标和风险边界的可验收补充；仍需重新核对任务与回执。
- 主版本增加：目标、范围、流程、数据、安全、兼容或不可逆结果变化；必须重新审核。
- 不覆盖旧版结论。Git 保留历史，当前文档明确链接被替代版本和变更摘要。

## 代码版本与兼容

- 三个发布单元分别使用 `mac-vX.Y.Z`、`win-vX.Y.Z`、`backend-vX.Y.Z`。
- 跨单元发布使用协调发布记录，列出确切版本、兼容矩阵、发布顺序和回退顺序。
- 后端接口先保持对已发布客户端的向后兼容，再发布客户端；旧接口清理是后续独立需求。
- 单个发布单元只有在无依赖阻断、数据兼容且回退验证通过时才能独立回退，否则执行协调回退或前滚。

## 提交与 PR

- 每个提交只包含当前任务批准范围，提交信息包含需求/任务编号和易读摘要。
- PR 必须链接需求版本、任务、用户回执、发布单元、验证证据、文档、兼容和回退计划。
- 用户在合并关键节点确认代码后，使用绑定准确内容提交 SHA 与当前范围的 `code` 回执记录同一次决定；未提交工作区、其他提交或旧 PR 结论不能替代。
- 未运行、失败、超时或环境缺失的检查不能勾选为完成；有效豁免必须显示为 `WAIVED` 并链接用户回执。
- 禁止 `--no-verify`、隐藏失败、降低标准、删除测试或关闭 Hook/CI。
- 完整 local gate 通过后，普通任务通过 `taskctl commit-task --manifest <当前任务变更清单>` 只提交清单中的精确文件并生成 A/B；未列入清单的用户文件保持原样，已有无关暂存内容阻断。`taskctl push-task` 仅对当前功能分支做非强制快进，不要求清理未提交的其他用户文件，也不需要逐项用户确认。合并、部署和发布仍须用户明确决定。

`local` 结果绑定冻结的 `workspace_digest`；`precommit` 是同一摘要上的只读核对报告，不是独立验证结果；`ci` 绑定内容提交 A 与事件 base/head；`post_merge` 绑定合并后的主分支内容提交。三类结果不得跨阶段或跨提交复用。`taskctl` 追加机器记录后可形成控制提交 B，CI 必须证明 A 是 B 的祖先且 A..B 仅包含受保护状态记录。PR detached HEAD 时使用事件 payload 和可信 `GITHUB_BASE_REF`/`GITHUB_HEAD_REF`，push 使用事件 `before`/`after`。

本地 PASS 必须通过 `taskctl run-validation` 或 `run-required` 的受控 runner，按任务审核过的 argv、超时和发布单元执行并从真实退出状态派生；公开 `record-validation --status passed` 拒绝自报。`ci` / `post_merge` PASS 只能由 `taskctl sync-github-run` 使用仓库外 Actions 只读凭据在线核对私有 GitHub 仓库的固定 workflow、run attempt、事件、分支、head SHA 和必需 job 后写入。缺网络/凭据、字段不符或只有 URL/日志时保持阻断。

## 完成条件

只有以下条件全部成立才可完成任务：范围内实现与文档齐全；全部批准验证为受控派生的 `PASS` 或具有有效用户对话豁免；`reconcile` 无阻断；私有 GitHub REST 核验后的 PR 与主分支 CI 通过；各发布单元的验证、兼容与回退证据齐全；真实 macOS/Windows 产品验收没有被 runner 结果替代；未决事项已关闭或明确阻断后续阶段。

达到 `LOCAL_VERIFIED` 后普通写入冻结。同一范围且尚未提交时可直接运行 `taskctl reopen` 归档旧结果并重跑验证；范围变化改用 `revise-scope`。提交后范围变化使用新任务，同范围 CI 失败则用 `recover-blocked` 保留历史并追加修复提交。
