# 治理总则-GOV-0001-v1.0

## 目的与适用范围

本规则适用于仓库中的治理、客户端共享代码、macOS、Windows 和后端工作。它确保每次变更都有需求、任务、审核、范围、验证、回退和历史，不因单人维护或 Agent 自动化而省略。

## 角色与权限

| 角色 | 可以做 | 不可以做 |
| --- | --- | --- |
| 用户 | 给出需求和高风险决定；批准验证豁免、不可逆操作、敏感数据或显著安全/成本/兼容风险、合并、部署和发布 | 清晰需求不重复确认；不逐项批准范围内本地工作或可逆技术默认值 |
| Codex | 只读检查；准备需求/任务/审核材料；在有效回执范围内实现和验证；如实报告 | 代签用户回执；自行跳过验证；扩大范围；隐藏内部失败；覆盖用户内容 |
| CI | 在干净环境重跑已定义的自动验证并报告结果 | 替代用户审核；把未执行项当通过；把 Windows runner 当成真实 Windows 产品验收 |

用户是唯一审核人。提交记录、对话文字或 Agent 自述不能替代由 `reviewctl` 验证的回执。

## 四类记录

- 需求：说明为什么做、做什么、不做什么、流程、风险、验收和版本。
- 任务：说明这一次在哪个分支修改哪些路径、依赖什么、如何验证和回退。
- 审核回执：证明用户批准了任务绑定的确切范围和验证计划。
- 核对结果：证明某一时刻文件、Git、任务、回执和验证记录相互一致。

文档是规则和意图，`project-control/` 是当前机器状态，Git 是文件历史，CI 是提交后验证证据。任何两者冲突都应由 `reconcile` 报告并阻止继续工作，不设置“静默优先级”。

`project-control/tasks/**`、`project-control/reviews/**` 和 `project-control/current-task.json` 是受保护记录，禁止直接编辑、覆盖、删除或通过通用写工具生成。任务和当前任务只能经 `taskctl` 写入；回执只能经用户控制的 `reviewctl` 流程写入。状态损坏时保留现场并建立治理修复任务，不能手工把 JSON 改成“正确状态”。

## 状态和流转

标准状态：

`DRAFT → REVIEW_PENDING → APPROVED → READY → IN_PROGRESS → LOCAL_VERIFIED → COMMITTED → CI_VERIFIED → CODE_REVIEWED → MERGED → POST_MERGE_VERIFIED → DONE`

- 只通过 `taskctl` 执行合法流转，并留下时间和原因。
- `APPROVED` 只表示可以按回执范围开工，不表示实现或验证完成。
- `READY` 表示审核内容、依赖和工作区已核对，可以进入实现。
- `LOCAL_VERIFIED` 需要本地批准验证全部通过或拥有有效用户豁免。
- `CI_VERIFIED` 和 `POST_MERGE_VERIFIED` 需要对应提交的 CI 结果，不得复用其他提交的绿色结果。
- `CODE_REVIEWED` 表示用户已经复核当前提交和批准范围，不能由 Agent 自行推进。
- 范围、需求版本、允许路径、验证计划、数据、安全、成本、兼容或不可逆结果变化时，使用 `taskctl revise-scope` 递增范围版本并返回 `DRAFT` 或 `REVIEW_PENDING`；旧回执自动失效。普通状态流转禁止倒退。
- 达到 `LOCAL_VERIFIED` 后普通源代码、文档和配置冻结。同一范围返工必须先经受控流程使受影响证据失效；范围变化必须执行 `revise-scope` 并重新审核，不能先修改再补状态。
- 需求批准前可在需求、决策和 proposal 目录准备本地文件；`BLOCKED` 仅允许当前任务恢复 proposal，终止状态只读。实现文件仍须等任务进入 `IN_PROGRESS`。用户需求清晰时，其请求本身就是范围决定；进入当前范围后，本地创建、编辑、测试和同范围返工不逐项审批。
- 关键确认点限定为需求定稿、脚手架/依赖/重大架构、登录与个人数据/安全/成本/不兼容迁移、验证豁免、不可逆操作以及合并/部署/发布。完整验证后的受控提交和功能分支非强制 push 不单独索取确认。

## 会话和工具门禁

- `.codex/hooks.json` 配置 `SessionStart` 和 `PreToolUse`。
- 项目 Hook 需要用户通过 Codex `/hooks` 审查并信任；配置文件或本地脚本测试通过不等于新会话已经加载。Hook 内容变化后按 Codex 信任流程重新核对。
- `SessionStart` 在启动、恢复、清空和压缩场景注入当前任务；异常时注入明确阻断。
- `PreToolUse` 在执行前核对任务、回执、阶段、分支和范围；未知、解析失败或状态损坏时按拒绝处理。
- `taskctl` 管理任务，`reviewctl` 管理回执，`reconcile` 只核对状态且不静默修复。
- Hook 只覆盖实际进入 SessionStart/PreToolUse 的 Codex 调用；已获准程序启动的子进程、用户外部终端和其他未接入路径不会自动再次经过 Hook。
- Hook 是项目工作流门禁，仍需受保护分支、受控 runner、绑定回执、CI 和用户审核共同约束，不把它描述为不可绕过的系统安全边界。

`reviewctl` 不提供“创建审核申请”命令。审核申请由版本化需求、任务范围、验证/回退计划和 `REVIEW_PENDING` 状态组成。用户在当前 Codex 对话中明确决定后，Codex 使用 `record-conversation` 记录对话引用、用户原话摘要和原因；工具自动从当前状态派生 scope、提交、检查项、阶段、环境、工作区摘要或操作目标。`list`、`show`、`verify` 保持只读，旧 `record` / `waive` 保持禁用。

`conversation-v1` 回执是审计绑定，不是用户身份的密码学证明。`approver=user`、对话引用和 `recorded_by=Codex` 只能说明记录内容，不能证明人在场；同一操作系统身份下的恶意进程仍可能伪造这些字段。用户在了解该弱化边界后明确选择对话审批。系统继续以受保护机器路径、Hook 覆盖的调用、scope/提交/摘要绑定、受控 runner、CI、分支保护和人工复核降低风险，不声称消除了同机冒充风险。

`GOV-0001-R001` 是初始兼容记录，R002 建立 OpenSSH 信任锚，R003 是摘要固定且已验签的最后一次迁移回执。R003 授权从 scope v3 起采用对话审批；项目策略、R003 摘要或历史验签材料发生漂移时失败关闭。历史 OpenSSH 公钥和验签实现仅用于复验 R002/R003，不再要求用户为后续审批生成签名。

## G0 根信任初始化

仓库起初没有工具可验证工具本身。用户已明确批准 G0 方向，因此首次初始化可在空仓库工作区创建且仅创建：治理工具、Hook、机器记录、本文档结构和治理 CI。

G0 不授权应用脚手架、应用依赖、业务代码、数据库迁移、提交或 push。G0 必须先运行自测和人工行为验证，向用户展示范围与结果；只有用户再次授权后才能形成首个提交和推送。此初始化例外在 G0 完成后永久结束。

## 范围和命名

- 需求目录：`<需求名>-<REQ-ID>/`；主文档：`<需求名>-<REQ-ID>-v<版本>.md`。
- 任务分别记录工作分支与目标 `base_branch`。工作分支使用同一 REQ-ID/TASK-ID，格式为 `codex/<req-id>-<task-id>-<readable-slug>`；除列明的 G0 bootstrap 外不得与 base branch 相同。
- 一个可独立验收功能点对应一个分支和 PR；跨发布单元使用协调任务与分单元任务。
- 名称使用产品和使用者能理解的稳定词语，缩写只用于固定编号，不堆叠专业术语。

## 审核回执和失效

开工回执至少绑定项目/源仓库、回执和任务编号、需求版本、目标、范围摘要、允许/禁止路径、分支、发布单元、验证计划、回退计划、用户决定、对话引用、决定/有效时间。合并关键节点的代码审核使用 `code` 回执，绑定准确内容提交 SHA 与当前范围；同一次明确合并决定可以形成该审计回执，不要求此前再做一次独立确认。验证豁免使用 `validation_waiver` 回执，绑定任务、当前范围、准确检查项、证据阶段、工作区摘要或提交、环境、门禁、原因和未来到期时间。未提交的同范围返工由 `taskctl reopen` 归档旧验证结果，不再要求单独 `rework` 回执；历史回执继续保留。

删除历史、破坏性迁移、强制覆盖或其他不可恢复动作需要用户明确对话决定和单独的 `irreversible_operation` 回执。G0 回执绑定唯一操作编号、当前范围、规范化操作材料的 `target_digest` 和有效期；操作材料必须列出准确目标、动作/命令、影响与最坏后果、备份/恢复方案和工作区摘要或提交。G0 尚无执行与单次消费器，所以回执只能核验用户决定，不能使不可逆命令变为可执行；首次使用前必须另建并审核专用治理需求。

出现以下任一情况回执失效：绑定内容变化；摘要不匹配；超过有效期；审核人不是用户；任务或需求被替代；分支/路径不符；新增高影响未决事项；状态文件损坏。Agent 不得修补或复制旧回执，必须生成新申请交给用户。

新对话回执在项目策略、R003 迁移根、项目/仓库、当前任务、范围和类型专属字段全部核对后才原子创建且不得覆盖现有编号；任一检查失败不留下有效回执。历史签名回执仍只信任任务中的 `review_authority` 复验，不从回执自带字段取得公钥。

## 文档完整性

- 开工前有版本化需求、任务范围、图示流程、假设/未决事项、验证和回退计划。
- UI 需求使用用户流程图并补齐全部交互状态；后端、数据、运维采用合适的时序图、状态图或数据流图。
- 模板默认章节不可省略。不适用项必须注明理由和确认人。
- 需求、开发、运维、排障、决策和治理分别维护；实现后同步受影响文档。
- `reconcile` 的文档门禁至少检查七类目录与入口、需求目录/文件命名、24 个默认章节、每节非空、适用图示与文字说明、无未处理占位、假设和未决事项清单以及本地链接。模板可保留填表占位，待审核或已批准需求不可保留。

## CI 与分支保护建议

- G0 的 push 与 PR 都按发布单元同时运行 Linux、macOS 和 Windows 治理检查；合并到主分支后由 push 再验证。后续需求若按成本缩减矩阵，必须另行审核并保留各发布单元证据。
- 主分支保护要求治理检查成功、分支最新、禁止强推和禁止绕过。单人项目的用户审核以 `reviewctl` 回执为准，不能依赖作者自批 PR。
- CI 只重验自动化证据，不授予开工、合并或发布权限。
- 私有仓库的 `ci` 和 `post_merge` PASS 只能由 `taskctl sync-github-run` 使用用户在仓库外配置的 Actions 只读凭据，通过 GitHub REST API 核对固定仓库、workflow、run attempt、事件、分支、head SHA 和必需 job 全部成功后写入；调用者提供的 URL、结论或日志片段不能形成证据。无网络、无凭据或响应不匹配时失败关闭，凭据不得进入仓库、任务记录或日志。
- CI 用事件 payload 的 base/head SHA 核对已提交 diff。任务内容提交 A 与随后只含受保护机器记录的控制提交 B 分开报告；B 必须包含 A，A..B 若出现普通内容变化即失败。PR detached HEAD 必须使用可信的 `GITHUB_BASE_REF`、`GITHUB_HEAD_REF` 和事件 base/head，不能把临时 merge ref 当任务分支；push 使用事件 `before`/`after`，首次 push 的全零 `before` 必须显式处理。

本地、CI 和合并后结果分别绑定工作区摘要或准确内容提交，不能跨阶段、跨范围或跨提交复用。precommit 只是同一冻结 local 摘要的只读派生报告。workflow 定义和本地绿色结果不等于 GitHub CI 已执行；没有真实 run 时保持 `PENDING`。

多发布单元任务必须在受审核验证计划和协调记录中逐一绑定受影响的 `mac`、`win`、`backend`，分别保存验证、兼容、发布和回退证据。PR 在 `windows-latest` 运行治理脚本只证明治理入口的 Windows 兼容性，不证明 Windows 客户端已在真实 Windows 环境完成安装、升级、卸载、系统安全存储或业务行为验收。

## 完成和历史

任务只有在范围、需求、分支、文件、审核、验证、CI、兼容、回退和文档一致时完成。变更历史保存在任务、Git 和决策记录；代码注释只记录长期有效的原因、不变量、兼容要求和前后置条件。
