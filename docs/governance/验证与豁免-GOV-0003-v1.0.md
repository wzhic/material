# 验证与豁免-GOV-0003-v1.0

## 核心规则

所有任务在开工前明确验证范围，执行时不得自行删减。`未运行`、`失败`、`超时`、`环境缺失`、`取消` 和 `SKIPPED` 均不是 `PASS`。

验证结果只使用：

- `PASS`：批准的检查在指定提交和环境真实执行，结果满足预期且证据完整。
- `FAIL`：执行失败或结果不满足预期。
- `BLOCKED`：环境、依赖、权限或未决事项使检查无法执行。
- `WAIVED`：用户明确接受某项未执行验证的风险；它仍不是通过。

当前实现状态：公开 `record-validation --status passed` 已永久拒绝，调用者不能自报成功。本地 PASS 只能由 `taskctl run-validation` 或 `taskctl run-required --phase local` 调用受控 runner 后派生；CI/合并后 PASS 只能由 `taskctl sync-github-run` 在线核验真实 GitHub Actions run 后写入。R003 已完成最后一次签名迁移，scope v3 起审核和豁免采用对话回执；R003 的完整规范化签名回执由固定 SHA256 封存，后续对话回执核验不再依赖各 runner 重跑 OpenSSH。R004 是精确绑定 scope v4 的首份对话 scope 回执。R005 授权首次 G0 CI 协议，R006 授权受控提交传输，R007 授权修复真实 Windows Run `32221854668` 的 Git UTF-8 解码失败；R009 取代路径集合不完整的 R008，授权修复 Run `32223213198` 暴露的 CP1252 标准输出与无 HOME Git 候选问题。控制提交 Run `32226753649` 的三平台失败由 R010 绑定规范化 recovery proposal，使用 `taskctl recover-committed` 归档旧证据并要求全部重跑。内容提交 `63b6de3b4e85b6cd6c2be8bbd43586197cec57ba` 的 Run `32230013274` 在尚未形成控制提交时出现 Windows 迁移根复验失败；R011 授权同范围返工，R012 绑定 schema v2 proposal，由 `recover-pending-content` 精确消费。R012 后形成的内容提交 `0b27ffaa178dd3ffc1ff0d53b899099126839e07` 在 Run `32233154643` 中由 Ubuntu/macOS 通过、Windows 因工作区摘要读取主机 POSIX 可执行位而失败。R013 授权最小同范围返工；R014 因 proposal 缺少完整固定安全不变量被恢复门禁拒绝，仅作为失败审计记录保留；R015 用完整不变量和固定摘要 `sha256:2f922bf6f97c847139fa21013e1016cc4eb21b5797a0176835b3a3c43b1583e3` 取代 R014 并已激活。上述恢复回执都不是验证豁免。每次 `taskctl reopen` 或恢复命令都归档当时结果，所有检查必须重新执行。

受控 runner 只接受任务范围中审核过的 argv 数组、超时和发布单元绑定，使用 `shell=False`、空 stdin、受限环境与临时 HOME 执行。结果由实际启动、退出码或超时派生，并只保存脱敏摘要、输出字节数/哈希和完整性结论；不保存调用者声称的 PASS。每次检查前后都核对 scope、确定性工作区摘要和受保护治理状态，发现被测命令改动任一对象时不落盘结果并失败关闭。

确定性工作区摘要对已跟踪普通文件使用 Git 索引中的 `100644/100755` 模式规范化可执行类别，而不读取不同宿主暴露的 POSIX 权限位；尚未进入索引的普通文件继续使用本机可执行位。这样同一提交在 Ubuntu、macOS 与 Windows 上得到相同摘要，同时 Git 中真实的可执行类别变化仍使旧证据失效。真实仓库索引无法读取、索引存在未合并条目或记录不可解析时失败关闭。

## 分层验证

| 层级 | 目的 | 典型证据 |
| --- | --- | --- |
| 治理单测 | 状态流转、回执完整性、越界检测、失败关闭 | 标准库 `unittest` 输出和退出码 |
| Hook 契约与行为 | 证明输入/输出契约、真实会话注入和工具执行前拒绝 | 标准库 `unittest`、脱敏输入/输出与实际允许/拒绝结果 |
| reconcile | 证明任务、回执、文件、分支、文档和验证一致 | JSON 报告、提交摘要、退出码 |
| 单元/集成 | 证明实现和依赖边界 | 任务批准的命令与报告 |
| 平台行为 | 证明 macOS/Windows 真实安装、升级、卸载和功能 | 真实平台/版本、产物摘要、步骤、截图/日志、结果；CI runner 不能替代 |
| 数据与持久化 | 证明 schema、迁移、保存、恢复和回退 | 真实数据库路径、前后状态、恢复证据 |
| 发布后 | 证明目标环境用户可见行为 | 版本、环境、关键流程、监控和回退检查 |

进程健康、容器健康、测试夹具或 UI 选中状态不能单独证明真实行为和持久化成功。

## 阶段与对象绑定

验证结果只按 `local`、`ci` 和 `post_merge` 三个阶段记录，任何一类都不能满足另一类阶段门禁。`precommit` 是针对已冻结 local 摘要生成的只读核对报告，不是第四类 `record-validation` 结果：

| 阶段 | 绑定对象 | 必需上下文 |
| --- | --- | --- |
| `local` | 当前规范化范围和确定性 `workspace_digest` | 命令、环境、时间、退出码、脱敏输出 |
| `precommit`（派生报告） | 与 local 相同的冻结工作区摘要 | 提交范围预检、当前分支、reconcile 报告；不能替代 local/ci |
| `ci` | 内容提交 A 与 GitHub 事件控制 head B | 事件 base/head、A..B 控制记录 diff、runner OS、run ID/URL |
| `post_merge` | 合并后的主分支 commit | push `before`/`after`、主分支、run ID/URL |

工作区、范围、提交或阶段改变时必须重新执行相应检查。达到 `LOCAL_VERIFIED` 后普通文件冻结；同一范围返工先使相关证据失效，范围变化使用 `taskctl revise-scope` 递增范围版本并重新审核。

## G0 必须验证

本地和 CI 都必须真实运行治理单测与核对：

```text
python3 -m unittest discover -s tools/governance/tests -p 'test_*.py' -v
python3 -m unittest discover -s .codex/tests -p 'test_*.py' -v
python3 tools/governance/reconcile.py static --json
python3 tools/governance/reconcile.py ci --json
```

`static` 在本地核对 `docs` 与 `workflow`，不依赖阶段验证结果；`ci` 必须由 GitHub Actions 带入可信事件上下文，本地无上下文时不得伪装为通过。

scope v2 起，上述命令不由调用者逐条执行再自报结果，而由 `taskctl run-required GOV-0001 --phase local` 按受审核 argv 执行并派生记录。scope v4 的对话审批与记录修正完成后必须重新运行全部本地检查；旧 scope 的结果只保留在任务修订历史中。

此外需要人工行为测试：

1. 新建/恢复/清空/压缩会话能注入准确任务，异常状态注入阻断。
2. 无回执、错误分支、越界路径、失效回执和损坏状态均在工具执行前被拒绝。
3. 范围、需求版本或验证计划变化使旧回执失效。
4. `reconcile` 对 drift/blocker/无效回执/缺文档/验证缺口退出 `1`；状态损坏或用法错误退出 `2`；只有无问题退出 `0`。
5. 任一测试目录为空时 CI 明确失败，不能以 `Ran 0 tests` 通过。

## CI 范围

- 每次 push 都按 `backend/Linux`、`mac/macOS`、`win/Windows` 三个发布单元运行治理检查。
- 每个 PR 同时运行 Linux、macOS 和 Windows 治理检查；矩阵中的每个环境都必须真实完成。
- 合并到主分支后的 push 再运行，结果绑定准确提交。
- CI 不安装应用依赖，不使用 `continue-on-error`，不通过条件表达式把必需检查跳过。
- 治理工具测试、Hook 契约测试和 `reconcile` 任一失败，workflow 失败。
- PR 必须用事件 payload 的 base/head SHA 计算已提交范围，并用可信 `GITHUB_BASE_REF`/`GITHUB_HEAD_REF` 判断分支；detached HEAD 或临时 merge ref 不能作为任务分支。push 使用事件 `before`/`after`，首次 push 的全零 `before` 走显式处理。
- `windows-latest` 的治理 job 只证明 Python 治理入口和 Hook 契约可在该 runner 上执行，不是 Windows 客户端的真实安装、升级、卸载、凭据存储或业务验收证据。

任务记录无法在一个 Git 提交中写入该提交自己的 SHA，因此采用两层提交证据：`task.git.committed_sha` 指向内容提交 A；`taskctl` 随后追加状态或证据所形成的事件 head 是控制提交 B。CI 必须证明 A 是 B 的祖先；若 B 不等于 A，A..B 只能修改 `project-control/tasks/**`、`project-control/reviews/**` 或 `project-control/current-task.json`，并同时报告 `content_subject_sha` 与 `control_head_sha`。A 之后出现普通内容变化即失败。

空仓库的首次 G0 push 采用一个精确而不扩权的闭环：

1. 根提交 A 必须是 `GOV-0001` 在 `main` 的完整治理快照；CI 按每个发布单元真实运行批准的全部检查，并核对根快照所有路径均在 scope 内，但 `taskctl run-required --bootstrap-first-push` 只返回 `bootstrap_pending`，不持久化 CI PASS，也不能推进 `CI_VERIFIED`。
2. 根 A 的 Run `32221854668` 失败后保留历史，不改写提交。R007 只允许 A 的一个固定消息、精确路径白名单的直接子提交 C `7b18bb4c0b3cc42e078acf5351a19f6760beea0f`；它只能非强制快进，CI 返回 `bootstrap_repair_pending` 且不写 PASS。
3. C 的 Run `32223213198` 再次失败后仍保留 A、C 和两个失败 run。R009 取代路径集合不完整的 R008，只允许从 C 形成修复 CP1252 输出与无 HOME Git 发现边界的固定消息、精确路径白名单直接子提交 D `d5e868de165ff4cd31459e13b4bb12535e0876a1`；D 只能非强制快进，并继续返回 `bootstrap_repair_pending`。

Codex 不能直接执行 G0 `git commit` 或 `git push`。`taskctl bootstrap-commit/bootstrap-push` 是唯一传输入口：content 阶段要求 `LOCAL_VERIFIED`、完整 local gate 和 precommit；初始提交要求空历史，R007/R009 历史恢复要求固定合同，R010 起的提交后恢复要求有效 proposal、匹配回执、活动恢复记录、准确失败控制父提交、固定消息和精确白名单。control 阶段要求 `COMMITTED`、HEAD 正好从记录的内容提交开始、所有工作区与提交差异均为受保护机器记录；远端 main 必须仍等于内容提交。工具只使用非强制 fast-forward push，通过 GitHub 官方 SSH 443 端点传输，同时把 `origin` 固定为审核的仓库标识。

G0 bootstrap 与控制提交的 push 在三个 runner 全量执行，确保正式记录 CI 证据前覆盖 Linux、macOS 和 Windows；后续普通需求是否缩减 push 矩阵必须另行审核，不能在 G0 中静默降低。

私有仓库的在线证据采用固定 GitHub REST 信任锚。`taskctl sync-github-run` 只接受 run ID、attempt、事件和 head SHA 作为定位信息，真正的仓库、workflow path、分支、状态/结论、commit 和必需 job 都从 GitHub 响应中交叉核对；调用者传入的 URL 或 `success` 字符串一律不能作证。用户在仓库外为 `MATERIAL_GITHUB_ACTIONS_READ_TOKEN` 配置仅 Actions/metadata 读取所需的最小权限凭据；工具只在 Authorization header 使用，不能把凭据写入仓库、证据、错误或日志。无网络、无凭据、响应不完整或任一字段不符时保持 `BLOCKED`，不得降级为离线自报。

## 豁免流程

只有用户可以决定是否豁免。发现必须跳过时先停止任务，说明：无法执行的检查、阶段、工作区摘要或提交、原因、受影响范围、最坏可能后果、已尝试方案、替代证据、建议有效期和补验计划。用户在当前 Codex 对话中明确同意后，Codex 才可用 `reviewctl record-conversation --kind validation_waiver` 生成自动绑定这些字段的回执；回执必须设置未来到期时间，旧 `record` / `waive` 入口继续拒绝。

仅写 `--approver user`、`recorded_by=Codex` 或复制对话文字都不构成身份凭证。`conversation-v1` 是用户选择的审计模型，不能抵抗同一操作系统身份下的恶意进程；机器门禁只验证 R003 迁移根、当前范围、检查项、阶段、摘要/提交、环境、门禁和有效期。该限制必须在每次高风险豁免说明中保持可见。

豁免回执的机器强制字段至少包含：回执编号、任务与需求版本、准确检查项、证据阶段、当前 `workspace_digest` 或目标提交、环境、理由、该阶段对应的最远门禁、到期时间、用户身份和范围摘要。已知风险、替代证据和补验触发条件写入回执理由或其 `confirmation_source` 指向的审核材料，不得只存在于口头说明。

- 豁免只作用于列明检查，不扩展需求和文件范围。
- 范围、提交、环境或风险变化时失效。
- `taskctl` 只允许在 `skipped` 结果引用当前有效豁免时记录；门禁和报告显示为 `WAIVED`，绝不转换成 `PASS`，PR 和发布说明必须显式展示。
- 到期或触发补验条件后恢复为 `BLOCKED`，不得自动续期。
- 不可逆操作还需要独立的用户操作回执，验证豁免不能替代。

代码审核和不可逆操作也不能由其他回执代替：

- `code` 回执绑定准确 commit SHA、当前 `scope_hash` 和用户结论；commit 变化即失效。
- `irreversible_operation` 回执在 G0 绑定唯一操作编号、当前范围、规范化操作材料的 `target_digest` 与有效期。规范化材料必须包含准确目标、动作/命令、影响、最坏后果、恢复方案和工作区摘要或提交。除 R010 精确 recovery proposal 的 `recover-committed` 专用消费器外，G0 不提供执行或单次消费器，所以其他有效回执也不会自动授权任何工具执行；首次使用其他不可逆操作前必须另建治理需求实现并验证专用的单次消费通道。R010 恢复记录只有在 GitHub REST 核验三平台 CI 成功后才转为 `consumed` 并绑定 content/control/run；后续按 `consumed_at` 核对操作发生时回执有效，不因自然到期改写历史。

## 证据要求

每项验证记录任务、需求版本、范围摘要、证据阶段、工作区摘要或提交、审核 argv、环境、开始/结束时间、退出码或超时、结果、输出哈希/大小、完整性检查和执行来源。`ci`/`post_merge` 结果还必须由 `taskctl sync-github-run` 绑定 GitHub REST 核验得到的 run ID/attempt、URL、事件、分支、head SHA、workflow 和 job 集合；缺任一项不得写成对应阶段证据。证据不能包含密码、令牌、私钥或个人数据。

多发布单元任务的每项检查必须在审核范围中列出覆盖的发布单元，调用时按受影响的 `mac`、`win`、`backend` 分别形成结果或由明确覆盖所有单元的检查证明。协调记录还必须逐单元关联兼容与回退检查；共享代码或某一个平台绿色不能替代其他发布单元的证据。

重复运行必须保留失败事实和修复关联，不得只展示最后一次绿色结果来隐藏不稳定性。

workflow 文件存在、本地测试通过或日志片段都不能证明 GitHub CI 已运行。没有通过私有 GitHub REST 在线核验并绑定准确提交的真实 run attempt 时，CI 和跨平台状态保持 `PENDING`；即使 Windows 治理 job 绿色，真实 Windows 产品验收仍单独保持未完成。
