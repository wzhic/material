# 发布与回退-OPS-0001-v1.0

## 文档信息

| 项目 | 内容 |
| --- | --- |
| 编号/版本 | OPS-0001 / v1.0 |
| 状态 | 规划基线；尚无可发布应用 |
| 环境 | 客户端本地、后端公网 |
| 发布单元 | macOS、Windows、backend |

## 发布原则

- 三个发布单元独立构建、版本、验证、发布和回退，禁止用一个“项目版本”掩盖单元差异。
- 跨单元需求使用协调发布记录，但不取消单元自己的证据和回退边界。
- 发布前确认任务、版本、产物摘要、兼容矩阵、迁移、监控、回退条件和负责人，并停下取得用户的最终发布决定。
- CI 通过是必要条件，不等于真实用户环境验收；尤其 `windows-latest` 治理 job 只证明治理入口在 Windows runner 执行。macOS 和 Windows 客户端均需在真实或明确受控的目标系统上分别验证安装、启动、升级、卸载、系统安全存储和核心业务行为。
- 暂不上架商店，但不得封死签名、公证、安装包和未来商店发布所需的标识、升级渠道与权限设计。

删除历史、破坏性迁移、强制覆盖、无法恢复的密钥轮换或其他不可逆动作，必须在操作前向用户说明准确目标、影响、最坏后果和恢复方案，并取得对应决定。普通联网、构建、功能分支 push、PR 准备和可逆回退不需要逐项审批；最终部署与发布始终由用户决定。

## 版本与协调发布记录

单元版本格式：

- `mac-vX.Y.Z`
- `win-vX.Y.Z`
- `backend-vX.Y.Z`

协调记录至少包含：发布编号、协调任务与各单元实现任务、三个单元的目标版本或“不变”、接口/schema 兼容矩阵、部署顺序、观察窗口、回退触发条件、回退顺序、逐单元产物摘要、自动验证、真实平台验收和回退证据。

## 推荐发布顺序

1. 后端先部署保持向后兼容的版本，并完成健康、鉴权、旧客户端和回退验证。
2. 分别发布 macOS 和 Windows 客户端；每个平台独立观察安装、升级、登录、核心行为和本地数据。
3. 等支持窗口结束后，另建需求清理旧接口或兼容代码，不在当前发布顺带删除。

若需求不涉及某单元，协调记录写明“不变”及依据，而不是省略该单元。

## 单独回退条件

某一单元仅在以下条件全部满足时可单独回退：

- 没有其他单元依赖只能由新版本提供的行为；
- API、文件格式和本地/服务端数据向后兼容；
- 身份和会话仍可被旧版本正确处理；
- 已验证目标旧版本的安装/部署和关键路径；
- 回退不会跨越不可逆迁移点；
- 生产回退作为部署动作已取得用户决定；若包含不可逆操作，还需单独记录其目标、影响和恢复方案。

任一条件不满足时，建立协调任务进行回退或前滚修复，不得自行强退。普通同范围、可逆的前滚修复由 Codex 完成；只有涉及验证豁免、破坏性/不可逆操作、个人或敏感数据、显著安全风险、实质成本、不兼容迁移或最终部署/发布时，才停下让用户决定。

## SQLite 数据维护

- 每个客户端数据库包含明确的 schema 版本；macOS 与 Windows 的业务 schema 应保持一致，平台元数据例外需单独记录。
- 迁移前验证备份、磁盘空间、失败恢复和旧版本兼容；测试空库、典型库、边界数据和中断恢复。
- 不兼容迁移必须先明确不可回退点、数据导出/恢复方案和用户确认，不能把应用降级当作数据回退。
- 登录凭据和密钥使用 macOS Keychain、Windows Credential Manager 或经审核的等价系统存储，不得明文保存到 SQLite。
- 字段清单、加密、保留、导出和删除策略尚未确认，数据模型需求定稿前保持阻断。

## 后端数据和鉴权

- 后端不保存账号数据。若技术方案需要身份映射、用户资料或凭据持久化，先作为项目边界变更重新审核。
- 身份提供方、令牌生命周期、吊销、恢复和多设备行为未决，不能在 G0 中默认实现。
- 日志、指标和错误报告不得包含令牌、密码、私钥或可还原的个人数据。

## 环境与配置

公网后端的开发、测试、预发布和生产环境数量尚未确认。首次部署需求必须补齐环境隔离、秘密管理、域名/TLS、备份、监控、告警、容量、成本和恢复目标。

配置变化也需要行为验证和持久化验证；界面显示已选择或进程健康不能单独证明配置生效。

## 发布后验证

- 主分支 CI 通过且产物来自已验证提交；结果以 GitHub Actions 当前提交的必需检查为准，由 Codex 核对并报告，不要求用户发送 Run 链接、提供 Token 或抄写结果。
- 后端验证真实鉴权、接口行为、持久化边界和回退路径，而非只看进程/容器健康。
- 客户端分别验证全新安装、升级、登录失效、离线/重连、本地数据保持、崩溃恢复和卸载边界。
- 记录观察窗口和异常；任一必需项未执行时发布保持阻断或使用有效用户豁免，不能标为完全通过。

PR 的绿色结果不能替代合并后主分支与目标环境验证。发布后检查必须针对实际发布的主分支 commit 和产物；本地结果、PR head 或其他提交的绿色结果不得复用。

三个发布单元的证据不能合并成一个笼统“项目通过”。共享客户端检查可以声明同时覆盖 `mac` 与 `win`，但两个平台的安装/升级/卸载、签名、安全存储和回退仍分别留证；后端的部署、兼容和回退证据单独绑定 `backend`。
