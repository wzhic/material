# 分析记录备份恢复问题排查 TRB-0015 v1.0

## 1. 排障原则

先保留主库和现有备份，再核对页面状态、磁盘空间、目录权限、schema 与完整性。不得手工编辑 SQLite、降低 `user_version`、把普通文件改名成应用备份、删除唯一副本、绕过二次确认或关闭 IPC 来源校验。排障记录不得包含 API Key、模型凭据、绝对路径、素材字节、加密引用或报告正文。

## 2. 常见现象与安全恢复

| 现象 | 常见原因 | 安全恢复 |
| --- | --- | --- |
| 数据维护页无法读取 | 主库不可打开、版本过高或完整性失败 | 保留应用数据目录；检查权限和磁盘，使用兼容客户端；不要让应用建立空库覆盖 |
| 显示只读 | 用户目录或主库缺少写权限 | 恢复当前账户权限并重启；只读期间不创建或恢复备份 |
| 创建备份失败 | 空间不足、目录权限、在线备份或复验失败 | 主库保持不变；恢复空间或权限后重试，本次失败目标不会进入清单 |
| 备份显示“校验失败” | 文件损坏、截断或不再是 SQLite | 不恢复该备份；保留它用于只读取证，选择另一份健康备份 |
| 升级时提示迁移前备份失败 | checkpoint、复制、权限、空间或旧库完整性异常 | 原库不会迁移；恢复条件后重新启动，不手工修改 schema |
| 恢复失败 | 目标复验、安全备份、暂存、替换、迁移或恢复后复验失败 | 应用回滚原库；保留错误和所有健康备份，恢复空间或占用后重试 |
| 恢复后记录数量变少 | 目标备份创建时间早于当前记录 | 属于恢复语义；替换前数据保存在新生成的“恢复前安全备份”中 |
| 恢复后源素材需重新定位 | 文件移动或 `safeStorage` 上下文变化 | 报告仍可读；用系统选择器选择同一完整指纹文件，不扫描目录或保存明文路径 |

## 3. 启动时出现恢复临时文件

正常流程在成功后清理精确 UUID 命名的临时文件。若主库缺失且存在 `restore-old`，客户端会在打开数据库前恢复最新的应用旧库；若健康主库已存在，则通过完整性检查后清理精确命名遗留文件。不要在应用运行中手工移动这些文件。

名字相似但不满足 UUID 合同的文件不属于应用状态，客户端不会恢复或删除。若主库与旧库都存在但主库损坏，应停止操作并保留全部文件，不能凭修改时间手工覆盖；先在副本上完成 SQLite 完整性取证。

## 4. 备份内容与隐私核对

- 备份应包含确认报告、规则与产品快照、反馈、关系和加密素材引用计数。
- 备份不应包含源素材、API Key、模型凭据文件、临时工具产物或外部 PDF。
- Renderer、错误提示、日志和任务记录不得出现备份绝对路径、SQLite 正文或密文。
- 不同系统账户恢复后密文可能不能解密；必须显示“需重新定位”，不能退化保存明文。
- V1 不自动清理备份。磁盘紧张时先扩容或移动整个受控应用数据副本，永久删除策略需独立功能支持。

## 5. schema 迁移核对

当前 schema 为 v3。v1 或 v2 文件型数据库在任何结构变更前都应出现完整性通过的 `pre-migration` 备份；失败时旧库版本和内容保持不变。v1 按 v1→v2→v3 迁移，v2 按 v2→v3 迁移，旧报告 JSON 不重写。

恢复旧备份后会再次执行迁移保护，因此备份清单增加一份新的迁移前备份属于预期行为。禁止通过手工建表、删除引用表、关闭外键或直接写 `PRAGMA user_version` 消除错误。

## 6. 验证与升级

修复后至少验证：数据维护页完整性为正常、schema 为 v3、记录与反馈数量符合预期；可读取一条旧报告；可创建新备份且重新读取为可用；历史素材无法自动打开时能安全重新定位。平台发布前还需分别验证 macOS 与 Windows 的目录权限、安装升级、文件占用、磁盘满和中断恢复。
