# 治理门禁问题排查-TRB-0001-v1.0

## 使用边界

本文只处理 G0 的任务、审核、Hook、核对和 CI 问题。排障允许收集只读证据，不授权修改状态、关闭门禁、跳过验证、提交、push 或部署。

## 通用排查顺序

1. 记录现象、时间、当前任务、分支和刚执行的操作，不记录密钥或个人数据。
2. 运行对应工具的 `--help`，确认命令和参数，不凭记忆猜测。
3. 使用 `taskctl` 读取任务，使用 `reviewctl` 验证回执，再运行 `reconcile`。
4. 保存退出码和脱敏输出，区分真实规则阻断与工具故障。
5. 修复需要写入时先建立排障任务并获得用户回执。
6. 修复后复现原问题，运行治理单测和 `reconcile`，记录防复发措施。

全程禁止直接编辑 `project-control/tasks/**`、`project-control/reviews/**` 或 `project-control/current-task.json`。任务/当前任务只能由 `taskctl` 写入；用户在当前 Codex 对话中明确决定后，新回执只能由 `reviewctl record-conversation` 自动绑定并创建。旧 `reviewctl record` / `waive` 保持禁用。

## 常见现象

### SessionStart 没有注入任务

- 确认项目受信任且 `.codex/hooks.json` 被当前 Codex 会话加载。
- 核对触发场景是否为新建、恢复、清空或压缩会话。
- 只读检查当前任务状态是否缺失、损坏或存在多个活动任务。
- 查看 Hook 的脱敏错误；不得通过手工粘贴一个“已批准”上下文继续开发。
- 修复配置后重新开启/恢复会话并验证注入内容，而不是只执行脚本单测。

### PreToolUse 拒绝操作

- 把拒绝视为有效阻断，先读清原因和建议下一步。
- 核对当前任务阶段、用户回执、需求版本、分支、允许路径、验证计划和未决事项。
- 若实际范围需要扩大，更新需求/任务并请求用户重新审核；不要拆命令、换工具或改 Hook 规避。
- 若判断为误拒绝，建立治理修复任务并用测试证明不会放开未审核操作。

PreToolUse 只覆盖它实际收到的 Codex 工具调用。已获准程序中的子进程、用户外部终端或其他未接入路径没有再次经过 Hook，并不表示门禁“失效”；这些路径必须由绑定回执、受控 runner、专用 CLI、CI 和受保护分支分别约束。不要用一次 Hook 允许结果证明整个进程树都受控。

### 回执突然失效

- 比对任务绑定的需求版本、范围摘要、允许路径、验证计划、审核人和有效期。
- 检查是否发生任何高影响假设或文件范围变化；这类失效是预期行为。
- 不修补摘要或复制旧回执。更新需求和任务审核包，使任务进入 `REVIEW_PENDING` 后交用户判断；用户明确回复后，Codex 只能通过 `record-conversation` 记录当前决定，不能手改回执文件。

### 对话回执无法记录或验证

- 先核对 `project.review_policy` 是否精确为 `conversation-v1`，以及历史 `GOV-0001-R003` 的固定 payload 摘要仍能使用受审核公钥验签；R003 是对话策略的迁移根，不得删除或改写。
- 核对用户是否在当前对话中给出明确决定，命令是否包含非空 `--confirmation-ref`、`--confirmation-text`、原因、唯一回执编号和 `--actor Codex`。
- scope、code、validation waiver、rework 和 irreversible operation 各有不同绑定。状态、scope、提交、检查项、阶段、环境、冻结摘要、操作编号、目标摘要或有效期不匹配时应失败关闭。
- 重复 review ID、越过当前任务、直接修改 reviews 目录或调用旧 `record` / `waive` 均应拒绝。不要复制旧回执或修改文件名修复。
- 对话回执不是密码学身份凭证；如果风险需要证明人在场，应新建治理需求恢复外部签名、硬件确认或独立审批服务，不得临时把对话字段描述成强认证。

### LOCAL_VERIFIED 后需要返工

- 普通写入被冻结时不得先改文件。先说明返工原因、范围是否变化、旧证据为何失效和重新验证计划。
- 范围不变时，用户明确同意后记录绑定当前冻结摘要和未来有效期的 `rework` 对话回执，再运行 `taskctl reopen`；工具会归档并清空旧本地证据、返回 `IN_PROGRESS`。
- 范围变化必须使用 `taskctl revise-scope`，不能用 rework 回执代替新版 scope 审核；已有内容提交后不得 reopen，应另建任务。

### reconcile 报告漂移

- 按报告逐项核对文件、分支、阶段、任务、回执、文档和验证记录。
- 保留并行任务和用户已有改动；不要用清理工作区掩盖越界文件。
- `reconcile` 默认只报告、不修复。任何修复都必须属于获准任务。
- 退出码 `1` 表示发现 drift/blocker/无效回执等核对失败；退出码 `2` 表示状态损坏或命令用法错误。两者都不能继续开工。

### CI 失败或没有运行测试

- 确认 workflow 确实由 push/PR 触发，且日志包含治理工具单测、Hook 契约测试与 `reconcile` 三个真实执行步骤。
- 空测试目录、命令不存在、权限失败、超时和 runner 缺失都属于失败，不得当作跳过。
- 先在相同提交本地复现，再在独立修复任务中处理；不要重跑直到偶然变绿而不调查原因。
- PR 的 Linux、macOS、Windows 任一检查失败，都保持阻断。
- `windows-latest` 治理 job 绿色只证明治理入口在该 runner 上执行，不能替代真实 Windows 客户端安装、升级、卸载或业务行为验收；后者缺失时对应发布证据仍阻断。
- 核对日志中的事件 base/head 与实际 commit。PR runner 常处于 detached HEAD，必须使用事件 payload 的 base/head SHA 以及可信 `GITHUB_BASE_REF`/`GITHUB_HEAD_REF`；不得用 `git branch --show-current` 的空值或临时 merge ref 冒充任务分支。
- push 核对事件 `before`/`after`；首次 push 的全零 `before` 应走 workflow 的显式初始提交路径。缺少可信 base/head 时保持阻断。
- 空仓库 GOV-0001 的首次根提交 A 即使全部 job 绿色，也必须报告 `bootstrap_pending` 且不能写 CI PASS。确认任务仍为 `LOCAL_VERIFIED`、A 是根提交、完整快照都在 scope 后，再由 `taskctl` 记录内容提交并形成只含 `tasks/reviews/current-task` 的控制提交；控制提交必须再次运行全部检查并报告 `bootstrap_control_head`。首次内容 run 直接标 PASS、控制提交含普通文件或项目白名单不再精确时都属于协议错误。
- Actions Run `32221854668` 证明根 A `59a285c853099b817d5fafa3a1d50ddda5ae7ce8` 的 Windows job 因 CP1252 解码 Git UTF-8 输出失败。R007 只允许显式 UTF-8 Git 解码、对应回归、协议/文档记录，以及一个直接从 A 非强制快进的修复提交 C `7b18bb4c0b3cc42e078acf5351a19f6760beea0f`；该 run 仍报告 `bootstrap_repair_pending`，不写 CI PASS。
- Actions Run `32223213198` 证明 R007 已消除 Git 解码错误，但 C 的 Windows job 又暴露两项不同边界：治理 JSON/错误输出向 CP1252 `stdout` 写入中文时抛出 `UnicodeEncodeError`，以及最小环境无 HOME/USERPROFILE 时 `Path.home()` 抛出 `RuntimeError`。R009 取代路径集合不完整的 R008，只允许统一 UTF-8 输出、无 HOME 时继续使用 PATH/当前运行时发现 Git、对应回归/文档，以及一个直接从 C 非强制快进的固定修复提交 D `d5e868de165ff4cd31459e13b4bb12535e0876a1`。
- Actions Run `32226753649` 在控制提交 `3e5e3e4dd9c2dcd5b76ef081913ba979dd94b762` 上三平台失败。Linux/macOS 的受控子环境缺少 `GITHUB_WORKFLOW_REF` 与 `MATERIAL_RELEASE_UNIT`；Windows 还暴露真实性断言未同步和绝对 Python 路径被 POSIX 分词吞掉反斜杠。应先记录 `BLOCKED from COMMITTED`，再用用户确认的 R010 绑定 recovery proposal；`recover-committed` 归档旧 PASS 后才允许修改，不能把失败 run 解释为通过。
- Actions Run `32230013274` 以内容提交 `63b6de3b4e85b6cd6c2be8bbd43586197cec57ba` 为 head：Ubuntu/macOS 成功，Windows 在 conversation-v1 审核核验时重跑系统 `ssh-keygen -Y verify` 并失败。由于控制提交尚未形成，任务如实记录为 `BLOCKED from LOCAL_VERIFIED`。先取得同范围 `rework` 回执 R011 并 `reopen`，再用 R012 绑定 schema v2 proposal；只有 `recover-pending-content` 可核对当前 HEAD、历史数量、上一恢复提交的直接子关系和空验证/Git 状态后替换活动恢复标记。修复采用完整规范化 R003 回执的固定 SHA256 封存：字段或签名变化仍失败关闭，但各 runner 不再依赖本机 OpenSSH 重新确认迁移根。
- Actions Run `32233154643` 以内容提交 `0b27ffaa178dd3ffc1ff0d53b899099126839e07` 为 head：Ubuntu/macOS 成功，Windows 在 `run-required` 阶段报告五项 local subject 不匹配。根因是已跟踪文件摘要直接使用宿主 `lstat` 的 POSIX 可执行位；Windows 与 POSIX checkout 对同一 Git `100644/100755` 模式给出不同结果。R013 只授权以 Git 索引模式规范化、补跨平台回归和更新相关记录。R014 因遗漏恢复合同的完整固定安全不变量被门禁拒绝，必须保留为失败审计；R015 以完整不变量和固定摘要取代后才可激活。排查同类问题时，应比较 `git ls-files --stage` 的索引模式而不是用本机 `chmod` 结果推断跨平台 subject；真实索引读取失败或存在未合并条目时保持阻断。
- Actions Run `32242354843` 以内容提交 `c4a3e656f405dcfb7bc6697963057d5bcba3bef6` 为 head：Ubuntu/macOS 成功，Windows 仍在 `run-required` 报告相同五项 local subject 不匹配。只读核对显示仓库全部条目均为 `100644`，因此上一轮“仅可执行位”诊断不完整；剩余差异是 Windows checkout 的 CRLF 与 POSIX LF 原始字节。R016 只授权同范围 Git 内容身份返工，R017 绑定失败 Run/HEAD、7 个历史提交、固定消息、9 个路径和完整不变量后取代 R015。修复必须对干净文件使用索引 blob，对已修改/未跟踪文件使用路径相关 Git clean-filter blob；测试须证明 LF/CRLF 与提交前后等价、真实内容变化仍失效。不得用 `.gitattributes` 或 workflow 变更掩盖本次摘要算法缺陷。
- 不得用空提交触发补跑、force push 改写任何历史、`--no-verify`、删除失败记录或手工编辑任务 SHA。历史 R007/R009 继续固定验证；后续恢复必须使用精确 proposal 摘要、当前 scope 的有效回执、准确失败 content/control SHA、Run、提交消息和路径白名单。proposal 漂移、额外路径、旁支或远端竞争都必须停止。
- 若直接 `git commit/push` 被拒绝，这是预期规则。检查是否正使用 `taskctl bootstrap-commit/bootstrap-push`、阶段是否为 content/control、任务状态是否为 LOCAL_VERIFIED/COMMITTED、远端是否为空、位于精确失败根或位于已记录内容提交。origin 不匹配、SSH 443 不可达、远端在检查后发生竞争或非快进时都必须停止，不能改用 force。
- 检查证据阶段：local 绑定工作区摘要；precommit 是同一冻结摘要的派生报告；ci 绑定内容提交 A 并同时核对事件控制 head B；post_merge 绑定合并后的主分支内容提交。发现跨阶段、跨提交复用，或 A..B 混入普通内容时，删除“已通过”声明但保留原历史，并重新运行对应阶段。

workflow 定义存在或本地测试绿色不代表 GitHub CI 已运行；没有真实 run ID/URL 和准确提交时，状态保持 `PENDING`。

### GitHub REST 同步失败

- 确认目标是固定私有仓库、固定治理 workflow 和准确 run attempt；调用者提供的 URL、`success` 字符串或日志片段都不是可信证据。
- 由用户在仓库外确认 `MATERIAL_GITHUB_ACTIONS_READ_TOKEN` 已配置且只有 Actions/metadata 读取所需的最小权限。不要把 token 写进命令记录、仓库、任务、截图或日志，也不要在排障输出中打印它。
- 核对网络、run ID/attempt、事件类型、head SHA、分支、workflow path 及必需 job 名称/结论。任一不一致、响应不完整或 API 不可达都应失败关闭。
- CI 阶段必须绑定内容提交 A 与控制 head B；post_merge 必须绑定合并后的主分支提交。修正定位信息不能把另一个 run 或旧绿色结果复用为当前证据。

## 禁止操作

不得删除或手工改写任务、回执、当前任务指针或验证历史，关闭 Hook/CI，使用 `--no-verify`，把失败改名为通过，暴露敏感信息，清理不属于当前任务的工作区内容，或在没有有效 `irreversible_operation` 用户回执时执行破坏性恢复。
